```
#2 關掉 DEMO ──► #5 建立評測 ──► #1 校準信心分數
   (先有真實判定)   (先有標準答案)   (有答案才能校準)
```

## 二、逐項修正方案

### 🔴 P0 — 問題 #2：預設回傳假資料（DEMO_MODE）

**現況**
- `app/config.py:60` → `DEMO_MODE: bool = True`（程式預設值是 True）
- `app/api/analyze.py:137 / 159 / 172`：
  - text → 永遠回紅框 `_get_demo_result("red")`
  - url → 永遠回黃框 `_get_demo_result("yellow")`
  - image → 永遠回綠框 `_get_demo_result("green")`
- 回傳結果與輸入內容**完全無關**，sources 鎖死 `https://www.google.com/`（`analyze.py:17`）

**問題**：展示模式方便 demo，但預設開啟代表系統「看起來會動、其實沒判斷」。

**修正方案**
1. `config.py` 預設改為 `DEMO_MODE: bool = False`，僅在離線展示時用 `.env` 顯式開啟。
2. 確認真實路徑可端到端跑通（`task_store` → `pandas_task_processor` → Gemini）。
3. 在前端／API 文件明確標示「展示模式」與「正式模式」差異，避免混淆。
4. （可選）保留 DEMO 但改成讀內容關鍵字的「離線規則判定」，而非無腦紅黃綠，讓離線展示也有意義。

**涉及檔案**：`app/config.py`、`app/api/analyze.py`
**工作量**：小（半天，含驗證）

### 🔴 P0 — 問題 #5：沒有任何評測指標（論文核心）

**現況**
- `scripts/test_ai_pipeline.py`：只跑**單一**寫死案例（台積電投資詐騙），print 出結果，**沒有比對標準答案**。
- 完全沒有 FP/FN、混淆矩陣、accuracy、precision/recall/F1。

**問題**：這是教授指定要的東西，也是論文「有效性」的唯一證據，目前不存在。

**修正方案（分四步，這是整份計畫最重要的部分）**

**Step 1：建立有標準答案的測試集**
- 收集 **150–300 筆**標註資料，欄位：`id, content, url, gold_label`（標準答案 = `SCAM / MISINFO / SAFE`）。
- 資料來源（皆有公開標註，可直接當 ground truth）：
  - `SCAM`：165 反詐騙公布案例、常見詐騙簡訊樣本
  - `MISINFO`：MyGoPen、台灣事實查核中心 (TFC)、Cofacts 已判定的假訊息
  - `SAFE`：gov.tw 公告、中央社 (CNA)、疾管署衛教
- 存成 `data/eval_set.csv` 或 `.jsonl`，注意**三類數量盡量平衡**。

**Step 2：撰寫評測腳本** `scripts/evaluate.py`
- 讀取 `eval_set.csv`，逐筆丟進**真實 pipeline**（DEMO_MODE 必須關閉）。
- 收集每筆 `predicted_label` 與 `confidence_score`，與 `gold_label` 比對。
- 加上**節流**（每筆間隔，避免 API 429）與**斷點續跑**（存中間結果，跑壞可續）。

**Step 3：用 scikit-learn 算指標**
```python
from sklearn.metrics import (
    confusion_matrix, classification_report, accuracy_score
)
# 三分類：SCAM / MISINFO / SAFE
print(classification_report(y_true, y_pred, digits=3))   # 每類 P/R/F1
cm = confusion_matrix(y_true, y_pred, labels=["SCAM","MISINFO","SAFE"])
acc = accuracy_score(y_true, y_pred)
# 二分類視角（風險 vs 安全）：另外算 TP/FP/FN/TN、precision、recall、specificity
```

**Step 4：產出論文用圖表**
- 混淆矩陣熱力圖（matplotlib / seaborn `heatmap`）→ `assets/confusion_matrix.png`
- 每類 precision / recall / F1 表格 → `data/eval_report.csv`
- Macro-F1、整體 accuracy、各類 FP/FN 計數
- （若做 #1 校準）ROC 曲線 / PR 曲線

**新增檔案**：`scripts/evaluate.py`、`data/eval_set.csv`、`data/eval_report.csv`、`assets/confusion_matrix.png`
**新增套件**：`scikit-learn`、`matplotlib`、`seaborn`（加進 `requirements.txt`）
**工作量**：中（2–3 天，主要花在標註資料蒐集）

### 🟠 P1 — 問題 #4：Google 搜尋被擋／限流

**現況**
- `app/services/crawler.py:309` 用 `googlesearch-python`（`from googlesearch import search`）爬 Google 結果。
- 結果經 `search_keyword_and_crawl()` → `similar_news` → 餵進 AI context（`pandas_task_processor.py:175`）當佐證。

**問題**：`googlesearch-python` 是爬 Google 網頁，會被擋／限流，不穩定，無法當正式 grounding。

**修正方案（建議 a + c 並用）**
- **(a) 改用 Gemini 原生 Google Search grounding（首選）**
  - Gemini 2.5 內建 `google_search` 工具，回傳結果附**官方引用來源 (grounding metadata)**。
  - 直接在 `_call_gemini_rest` 的 payload 加上 `"tools": [{"google_search": {}}]`，解析回傳的 `groundingMetadata` 當 sources。
  - 一次解決「搜尋」＋「引用」，且來源是真實 URL（順帶減輕 #1 的 URL 幻覺問題）。
- **(b) 備援：正式 Search API**
  - 專案**已預留** `SERPER_API_KEY`（`config.py:54`）。註冊 Serper.dev（免費額度）即可穩定取得 Google 結果。
  - 或用 Google Programmable Search Engine (CSE) 官方 API。
- **(c) 針對假訊息：直接打 Cofacts / TFC API 當主要佐證**
  - 假訊息類查核，Cofacts GraphQL 已在 `search_service.py` 用過，可作為 MISINFO 的權威來源。
- 移除正式流程對 `googlesearch-python` 的依賴（可留作離線 fallback）。

**涉及檔案**：`app/services/crawler.py`、`app/services/ai_service.py`、`app/services/search_service.py`、`requirements.txt`
**工作量**：中（1–2 天）

### 🟠 P1 — 問題 #1：confidence_score 不是校準後的機率

**現況**
- `ai_service.py`：`confidence_score` 由 Gemini 在 JSON 裡**自己回報**（prompt 第 90 行要求 0.0–1.0）。
- LLM 自評信心**普遍過度自信**，不是統計意義上的真實機率。

**問題**：把這個數字當「機率」呈現會誤導讀者。論文若寫「信心 95%」但實際命中率沒那麼高，會被質疑。

**修正方案（二擇一，建議先 A 後 B）**
- **(A) 誠實重新定位（立即可做）**
  - 前端／論文不再稱「機率」，改稱「**風險等級**」並用離散標籤：高 / 中 / 低（依分數分段）。
  - 在論文「研究限制」明確寫：`confidence_score 為模型自評，未經機率校準`。
  - 成本最低，立刻消除誤導。
- **(B) 真正做機率校準（進階，與 #5 共用資料集）**
  - 用 #5 的標註集，收集 (自評分數, 是否答對) 配對。
  - 畫**可靠度圖 (reliability diagram)**：把預測分數分箱，比較「平均信心」vs「實際正確率」。
  - 計算 **ECE (Expected Calibration Error)** 量化校準誤差。
  - 用 **Isotonic Regression** 或 **Platt scaling** 把原始分數映射成校準後機率。
  - 論文放「校準前 vs 校準後」可靠度圖，這是很漂亮的加分項。

> **相依**：(B) 必須先有 #5 的標註資料集才能做。

**涉及檔案**：`app/services/ai_service.py`、前端顯示、`scripts/evaluate.py`（加校準）
**工作量**：A 小（半天）／ B 中（1–2 天，跟 #5 一起做）

### 🟡 P2 — 問題 #6：影片只抓標題＋描述

**現況**
- `crawler.py:281`：`desc = info.get('description', '')` → 只用描述當 content。
- 諷刺的是 `crawler.py:274-279` **已經抓了** `subtitles` / `automatic_captions`，但後面根本沒用！

**問題**：沒把「影片裡講的話」轉成文字，等於沒分析到影片內容。

**修正方案（a 是低成本快贏）**
- **(a) 先用已抓到的自動字幕（快贏，半天）**
  - 既有程式已取得 `automatic_captions`，下載字幕軌（vtt/srt）→ 解析成純文字 → 併入 `content`。
  - 大多數 YouTube / 短影音都有自動字幕，免費、不需額外模型。
- **(b) 無字幕影片：語音轉文字 (ASR)**
  - 下載音軌，用 `faster-whisper`（本地、免費）或 **Gemini 2.5 直接吃音訊**（多模態）轉逐字稿。
  - 作為 (a) 沒有字幕時的 fallback。

**涉及檔案**：`app/services/crawler.py`、（b 需要）`requirements.txt`
**工作量**：a 小 / b 中

### 🟡 P2 — 問題 #3：只能 localhost、輪詢難接手機捷徑

**現況**
- 正式模式 async：先回 `task_id`，前端每 2 秒輪詢（`analyze.py` async 流程）。
- 只跑在 `localhost:8000`，手機連不到。

**問題**：iOS 捷徑要做兩段式（送出→輪詢）很麻煩；且 localhost 手機根本連不到。

**修正方案**
- **(a) 提供同步端點（給手機捷徑用）**
  - 新增 `POST /api/analyze/sync`：內部 `await` 跑完整 pipeline，**一次回傳最終結果**，捷徑只需打一次。
  - 設合理 timeout（如 60s），逾時回提示。
- **(b) 讓手機連得到**
  - 展示用：`ngrok` / `cloudflared` 開臨時公開 HTTPS 通道（5 分鐘搞定）。
  - 正式用：部署到 Render / Railway / Fly.io（專案已有 Dockerfile，可直接上）。
- **(c) 前端輪詢已修過記憶體洩漏**（`useRef` 清理），維持即可。

**涉及檔案**：`app/api/analyze.py`（新增 sync 端點）、部署設定
**工作量**：sync 端點小／公開部署中
